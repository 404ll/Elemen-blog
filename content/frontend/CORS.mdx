理解跨域问题，可以沿着「同源策略 → 跨域请求 → CORS → 预检请求 → Cookie 与 Credentials → 服务器代理」这条主线展开，用它解释实际项目中遇到的跨域报错。

## 一、什么是同源策略（Same-Origin Policy）？

同源策略是浏览器的一种安全机制，用于限制不同源之间的资源访问和数据交互，防止恶意网站未经授权读取其他网站的数据。

判断两个 URL 是否同源，需要同时满足三个条件：

- 协议（Protocol）一致。
- 域名（Host）一致。
- 端口（Port）一致。

例如，以 `https://www.example.com` 为基准：

| URL                            | 是否同源 | 原因    |
| ------------------------------ | ---- | ----- |
| `https://www.example.com/user` | 是    | 仅路径不同 |
| `http://www.example.com`       | 否    | 协议不同  |
| `https://api.example.com`      | 否    | 域名不同  |
| `https://www.example.com:8080` | 否    | 端口不同  |

需要特别注意，同源策略并不意味着浏览器完全禁止发送跨域请求。

例如：

```js
fetch('https://api.example.com/users')
```

当请求满足简单请求条件时，即使两个网站不同源，浏览器通常仍然会发送请求。服务器可能正常处理并返回 HTTP 200，但如果响应没有正确配置 CORS 响应头，浏览器就不会允许 JavaScript 读取响应内容。

因此，跨域问题的核心通常不是请求无法发送，而是浏览器是否允许当前页面读取跨源响应。

另外，同源策略不只作用于 `fetch`，也限制跨源 DOM 访问、部分浏览器存储访问等。图片、脚本等资源的跨源加载则有各自的规则，并非全部禁止。

## 二、什么是跨域？为什么浏览器需要限制？

当页面发起的请求与当前页面不满足同源条件时，就属于跨源请求，通常也称为跨域请求。

假设用户已经登录了银行网站 `https://bank.com`，浏览器保存了银行的 Session Cookie。此时用户访问了恶意网站 `https://evil.com`。

如果浏览器完全不限制跨源数据读取，恶意网站就可能通过 JavaScript 请求银行接口，读取用户的账户信息。

因此，浏览器需要限制不同源之间的数据交互。

但这里要进一步区分：

- 同源策略 / CORS：主要防止恶意网站的 JavaScript 未经授权读取跨源数据。
- CSRF 防护：防止恶意网站利用用户已有的登录凭证发起非预期操作。

同源策略本身不能完全防止 CSRF，因为某些跨源请求仍然可以发送。

## 三、跨域解决方案一：CORS

CORS（Cross-Origin Resource Sharing，跨源资源共享）是一套基于 HTTP 响应头的机制，允许服务器声明哪些来源可以读取它的资源。

CORS 由服务端声明访问策略，由浏览器负责执行检查。

例如，前端页面位于：

```text
https://www.example.com
```

请求的 API 位于：

```text
https://api.example.com
```

浏览器发送请求时，通常会携带 `Origin` 请求头：

```http
GET /users HTTP/1.1
Host: api.example.com
Origin: https://www.example.com
```

服务器在响应中配置：

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://www.example.com
Content-Type: application/json
```

浏览器收到响应后，检查 `Access-Control-Allow-Origin`，判断是否允许当前页面读取响应。

### 3.1 CORS 的主要 HTTP 响应头

| 响应头                                | 作用                         |
| ---------------------------------- | -------------------------- |
| `Access-Control-Allow-Origin`      | 指定允许访问的来源                  |
| `Access-Control-Allow-Methods`     | 指定预检允许的 HTTP 方法            |
| `Access-Control-Allow-Headers`     | 指定预检允许的请求头                 |
| `Access-Control-Allow-Credentials` | 是否允许浏览器暴露携带凭证的跨源响应         |
| `Access-Control-Max-Age`           | 设置预检结果的缓存时间                |
| `Access-Control-Expose-Headers`    | 指定允许前端 JavaScript 读取的额外响应头 |

最核心的是 `Access-Control-Allow-Origin`。

对于不需要携带凭证的公共 API，可以使用：

```http
Access-Control-Allow-Origin: *
```

表示允许任意来源读取符合 CORS 规则的响应。

## 四、简单请求与预检请求（Preflight）

CORS 请求还需要区分简单请求和需要预检的请求。

### 4.1 简单请求

简单请求需要同时满足一系列条件，例如：

- HTTP 方法是 `GET`、`HEAD` 或 `POST`。
- 仅使用 CORS 规范允许的安全列出请求头。
- 如果设置 `Content-Type`，其媒体类型需要是 `application/x-www-form-urlencoded`、`multipart/form-data` 或 `text/plain` 之一。
- 还需要满足其他规范限制。

例如普通的 GET 请求：

```js
fetch('https://api.example.com/users')
```

这种情况下，浏览器通常直接发送实际请求，再根据响应中的 CORS 头决定 JavaScript 能否读取结果。

### 4.2 非简单请求与 OPTIONS 预检

例如：

```js
fetch('https://api.example.com/users', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': 'Bearer token'
  },
  body: JSON.stringify({ name: 'Elemen' })
})
```

由于使用了 `application/json` 和 `Authorization` 等非 CORS 安全列出请求头，浏览器通常需要先发送 OPTIONS 预检请求：

```http
OPTIONS /users HTTP/1.1
Origin: https://www.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization,content-type
```

其中：

- `Access-Control-Request-Method`：告知服务器实际准备使用的 HTTP 方法。
- `Access-Control-Request-Headers`：告知服务器实际请求准备携带哪些非安全列出请求头。

服务器响应：

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://www.example.com
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Authorization, Content-Type
```

如果预检通过，浏览器才会发送实际 POST 请求。

注意，预检通过不代表实际响应可以无条件读取。浏览器仍然需要检查实际响应的 CORS 配置。

## 五、Cookie、Session 与 credentials

这是跨域中容易混淆的部分。

Fetch API 的 `credentials` 用于控制浏览器是否在请求中携带凭证，以及是否处理响应中的凭证信息。

它有三个取值：

| 值             | 含义             |
| ------------- | -------------- |
| `omit`        | 不携带凭证          |
| `same-origin` | 仅同源请求携带凭证，默认值  |
| `include`     | 同源和跨源请求都允许携带凭证 |

假设：

```text
前端：https://www.example.com
后端：https://api.example.com
```

后端使用 Session + Cookie 维护用户登录态。

如果前端直接调用：

```js
fetch('https://api.example.com/user')
```

由于 Fetch 默认使用 `credentials: 'same-origin'`，跨源请求不会携带 Cookie。

因此需要：

```js
fetch('https://api.example.com/user', {
  credentials: 'include'
})
```

但这并不代表跨域问题就解决了，服务端还必须配置：

```http
Access-Control-Allow-Origin: https://www.example.com
Access-Control-Allow-Credentials: true
```

并且此时 `Access-Control-Allow-Origin` 不能是 `*`。

另外，`credentials: 'include'` 只是允许携带符合条件的 Cookie，并不能绕过 `SameSite`、`Secure` 或浏览器第三方 Cookie 限制。

这里也需要区分跨源（Cross-Origin）和跨站（Cross-Site）：

- `https://www.example.com` → `https://api.example.com`：跨源，但通常属于同站。
- `https://www.example.com` → `https://other.com`：既跨源，也跨站。

对于跨站场景，Cookie 往往还需要配置 `SameSite=None; Secure` 才可能随请求发送。

如果使用 JWT 并由前端主动添加 `Authorization: Bearer token` 请求头，则不需要为了发送这个请求头而设置 `credentials: 'include'`。

## 六、跨域解决方案二：服务器代理

服务器代理的核心思想是：让浏览器请求同源的服务器，再由该服务器向目标 API 发起请求。

例如：

```text
浏览器 (localhost:5173)
       │
       │ GET /api/users
       ▼
Vite 开发服务器
       │
       │ GET https://api.example.com/users
       ▼
目标 API 服务器
       │
       ▼
Vite 代理返回响应
       │
       ▼
浏览器
```

由于浏览器访问的仍然是 `localhost:5173`，所以它看到的是同源请求。

代理服务器向目标 API 发送 HTTP 请求时，不受浏览器同源策略限制。

### 6.1 Vite 开发环境代理

```js
// vite.config.js
import { defineConfig } from 'vite'

export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'https://api.example.com',
        changeOrigin: true
      }
    }
  }
})
```

前端请求：

```js
fetch('/api/users')
```

Vite 会将请求代理到：

```text
https://api.example.com/api/users
```

注意，上面的配置会保留 `/api` 前缀。如果目标接口实际是 `/users`，还需要使用 `rewrite` 移除前缀。

另外，`changeOrigin: true` 主要用于修改代理请求中的 Host 等目标主机相关信息，而不是直接修改浏览器的同源策略。

### 6.2 生产环境代理

生产环境中，也可以使用 Nginx、API Gateway、BFF 或 Next.js 服务端路由完成代理。

所以不能简单理解为「开发环境用代理，生产环境用 CORS」。两种方案都可以在生产环境使用，具体取决于系统架构。

## 七、CORS 和服务器代理有什么区别？

| 比较维度              | CORS         | 服务器代理              |
| ----------------- | ------------ | ------------------ |
| 核心原理              | 服务端声明跨源访问策略  | 通过同源入口转发请求         |
| 浏览器是否直接跨源请求       | 是            | 通常否                |
| 是否需要浏览器执行 CORS 校验 | 是            | 同源代理请求通常不需要        |
| 前端改动              | 通常较少         | 请求地址需指向代理入口        |
| 后端配置              | CORS 响应头     | 代理服务与路由            |
| 常见应用              | 开放 API、前后端分离 | BFF、统一 API 入口、开发代理 |

需要补充的是，CORS 不是 API 的身份认证与授权机制。即使限制了允许访问的 Origin，服务端仍然必须正确验证用户身份和权限。

## 八、串起跨域请求的完整流程

同源策略是浏览器的一种安全机制，用于限制不同源之间的资源访问和数据交互。所谓同源，就是两个 URL 的协议、域名和端口都必须相同。

需要注意的是，同源策略并不是完全禁止跨域请求的发送，而是限制某些跨源交互，尤其是 JavaScript 读取跨域响应。例如，一个简单的跨域 GET 请求可能正常到达服务器，服务器也返回 HTTP 200，但如果响应没有正确配置 CORS 响应头，浏览器就会阻止前端读取响应数据。

常见的跨域解决方案主要有 CORS 和服务器代理。

CORS 是一种基于 HTTP 响应头的跨域资源共享机制。浏览器发送跨域请求时，通常会携带 Origin 请求头，服务端可以通过 Access-Control-Allow-Origin 指定允许访问的来源，浏览器根据响应头决定是否允许 JavaScript 读取数据。

对于简单请求，浏览器通常直接发送实际请求；对于非简单请求，比如携带 Authorization 请求头或者使用 application/json 的 POST 请求，浏览器通常会先发送 OPTIONS 预检，询问服务器是否允许对应的方法和请求头，预检通过后再发送实际请求。

如果跨源请求需要携带 Cookie，例如使用 Session + Cookie 维护登录态，还需要在 Fetch 中设置 credentials: 'include'，同时服务端配置 Access-Control-Allow-Credentials: true，并指定明确的允许来源，不能使用通配符。

另一种方案是服务器代理，让浏览器请求同源服务器，再由代理服务器转发到目标 API。由于同源策略主要由浏览器执行，因此服务器之间的 HTTP 通信不受浏览器同源策略限制。

实际开发中，可以使用 Vite 的 proxy 或 Next.js 的服务端能力进行代理；生产环境则可以根据业务需求选择配置 CORS，或者使用 Nginx、BFF、API Gateway 等方式统一 API 入口。

这套知识真正需要掌握的不是背诵所有响应头，而是能够清楚解释三个问题：为什么浏览器会限制跨源读取、CORS 如何让浏览器放行、服务器代理为什么能避开浏览器直接跨域。

如果这三个原理清楚了，再理解 OPTIONS 预检、Cookie 凭证、CSRF，以及实际项目中的跨域排查就会容易很多。
