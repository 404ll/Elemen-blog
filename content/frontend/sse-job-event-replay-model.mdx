在梳理 SSE 的时候，我一直卡在一个问题上：

**客户端已经告诉服务端自己处理到了哪条，服务端只补发这个 ID 之后的事件，为什么还要去重？**

如果客户端说已经处理到 120，服务端查询 `id > 120`，返回的应该是 121、122。那“重连后可能再次收到 120”是怎么发生的？

这个疑问让我继续往下追：断点续传究竟续的是什么，`lastEventId` 和 `processedIds` 分别记录什么，以及这些东西怎样放进一个完整的任务系统。

## 我知道带 ID 重连，但还说不清“续”的是什么

先保留一点必要的背景。SSE 通过一个持续打开的 HTTP 响应，把服务端产生的事件传给客户端。服务端返回 `Content-Type: text/event-stream`，随后持续写入响应体。一条带 ID 的事件可以长这样，最后用空行结束：

```text
id: 120
event: content
data: {"text":"第一段内容"}

```

协议中的 `id` 是字符串；下面为了方便讨论，约定它是**同一个任务内按顺序递增的整数**。

假设服务端已经产生了这些事件：

```text
118、119、120、121、122
```

客户端成功处理到 120，随后断网。页面还在，之前已经生成的内容也还在，只是收不到后面的事件。

重新连接时，客户端带上自己保存的位置：

```http
GET /jobs/job_001/events
Last-Event-ID: 120
```

服务端找到这个任务中 `eventId > 120` 的事件，补发 121、122，再继续传输后续产生的事件。

这里“续”的是**从上一次处理位置继续消费业务事件**。原来的网络连接已经断了，重新建立的是另一次请求。

但还有一个容易忽略的问题：服务端怎么找回 121、122？

120 只是一个位置，本身不包含后续内容。如果服务端当时只是把事件写进响应，没有保存任何历史，即使知道客户端停在 120，也没有内容可以补发。

所以断点续传需要两边配合：客户端记住位置，服务端保留这个位置之后可以重放的事件。

```text
客户端：我处理到了 120
服务端：我保存了 121、122，可以补给你
```

重新连上解决的是通信恢复，补回遗漏事件才解决数据恢复。

> 本文的 `lastEventId` 指应用自己维护的“最后成功处理位置”，适用于自行管理消费与重连的 fetch 客户端。原生 EventSource 自动维护的 ID 不会等待业务异步处理成功，不能直接当作业务确认。它的重连与 ID 行为见 [WHATWG SSE 规范](https://html.spec.whatwg.org/multipage/server-sent-events.html)。

## 既然只补发后面的，为什么还会重复？

理解到这里，我对“重连可能导致重复”还是有疑问。

如果最后处理到 120，告诉服务端的也是 120，查询条件又是 `id > 120`，那服务端确实不应该再补发 120。

**这个正常流程本身不会重复发送已确认的 120。** 需要继续追问的是：实际处理到的位置，和恢复后能够拿出来的位置，会不会不一样？

假设客户端需要把文章内容和消费位置保存下来，但分两次操作完成：

```text
已经保存的游标是 119
        ↓
收到 120，把它的内容追加到文章并保存成功
        ↓
还没保存 lastEventId = 120，页面崩溃
        ↓
重新打开后，只能恢复出游标 119
```

这时，120 的内容已经存在，但客户端重连时能提供的游标仍然是 119。

服务端执行 `id > 119`，自然会补发 120、121、122。它严格遵守了查询规则，120 仍然可能被客户端处理第二次。

| 情况 | 实际已保存的处理效果 | 重连携带的位置 | 服务端补发 |
| --- | --- | --- | --- |
| 正常恢复 | 到 120 | 120 | 121、122 |
| 保存过程中崩溃 | 到 120 | 119 | 120、121、122 |

这样，前面的矛盾就能解释了：**异常窗口里，业务处理的效果已经生效，记录下来的消费位置却落后了。**

这里要把“断网”和“崩溃”分开。仅仅断网，并不意味着本地代码无法继续更新变量。上面的重复场景成立，是因为处理结果已经保存，而游标保存失败或尚未完成，恢复时两者不一致。

如果内容和游标都只在内存里，刷新后两者一起丢失，那又是另一个问题：页面需要重新构建状态，不能直接假定之前的内容还在。

## 去重记录和消费游标，分别记录什么？

接着我追问的是 `processedIds`。如果第二次收到 120，凭什么知道它已经处理过？

先看重复处理会怎样影响结果。假设事件带来的内容是 `Hello`：

```js
article = event.data.text;
```

同一条事件执行两次，结果还是 `Hello`。但如果业务是追加片段：

```js
article += event.data.text;
```

重复处理后就成了 `HelloHello`。

这就是幂等在这个例子里的含义：**同一个操作执行多次，是否与执行一次产生相同的效果。** 进度条可以发送绝对值 `progress = 80`；流式正文经常需要追加片段，因此需要避免重复追加。

`processedIds` 可以记录已经成功应用的事件 ID。同一个页面会话内，一个简化的处理顺序是：

```js
// 仅示意：单任务、串行消费、同步且不产生部分写入的状态更新。
const processedIds = new Set();
let lastEventId = 0;

function consume(event) {
  if (processedIds.has(event.id)) return;

  applyEvent(event);
  processedIds.add(event.id);
  lastEventId = event.id;
}
```

这里需要记录的是“处理成功”，而不只是“收到过”。如果先记为已处理，再执行更新，更新失败后这条事件反而可能被跳过。

两个记录的用途可以这样区分：

- `processedIds` 回答：这一条事件已经成功应用过吗？
- `lastEventId` 回答：这条有序事件流已经成功处理到哪里，重连从哪里继续？

不过，不是每个系统都要同时保存这两个东西。如果事件严格有序、客户端串行处理，且游标代表此前事件都已经处理成功，那么 `event.id <= lastEventId` 就可以用于跳过旧事件。

还有一个边界：上面的内存 Set **解决不了前一节的跨崩溃问题**。页面重开后，Set 也没有了。即使单独保存 Set，处理效果与去重记录之间仍然可能出现保存不一致的窗口。

对于需要持久恢复的本地状态，可以把状态和游标作为一个检查点一致保存；对于会触发服务端副作用的操作，则需要在实际执行操作的服务中，通过幂等键等方式避免重复生效。不能用一个内存集合就宣称整个链路可靠了。

同样，覆盖赋值只保证同一事件重复执行的效果相同。旧进度晚于新进度到达，依然可能让页面倒退，所以顺序问题也需要处理。

## 我需要把它放回整套业务里

讨论到这里，单个函数已经不足以解释我的问题了。我当时又补了一句：

> 我的意思是关于这一整套的业务建模。

我想知道的是：任务由谁执行，连接断了以后谁继续保存内容，重新连接时又是谁负责找回事件。

拿 AI 写作任务来看，可以先认清这几个角色：

| 角色 | 职责 |
| --- | --- |
| Job | 标识这次任务，保存运行状态和结果位置 |
| Worker | 执行生成任务，产生业务事件 |
| Event Store | 保存按任务组织的事件，供后续读取 |
| SSE Endpoint | 把查询到的事件持续传给客户端 |
| Client | 应用事件，维护页面状态和消费位置 |

下面是简化的数据形状，不代表某个项目的完整实现：

```ts
type Job = {
  id: string;
  status: "queued" | "running" | "completed" | "failed";
  resultId?: string;
};

type JobEvent = {
  jobId: string;
  eventId: number;
  type: "progress" | "content" | "done" | "failed";
  payload: Record<string, unknown>;
};

type ClientState = {
  jobId: string;
  text: string;
  progress: number;
  lastEventId: number;
};
```

用户点击“生成文章”，服务端先创建 Job，返回 `job_001`，再由独立 Worker 执行。客户端根据 jobId 订阅事件：

```text
POST /jobs                 → 创建任务，返回 jobId
GET /jobs/job_001/events    → 接收任务事件
```

这种拆分下，创建任务用 POST，订阅仍然可以用 GET；具体选 EventSource 还是 fetch，取决于订阅接口是否需要自定义请求头等控制能力。

Worker 执行过程中，逐步保存事件：

| eventId | 事件 | 内容 |
| --- | --- | --- |
| 118 | progress | 正在分析资料，进度 20% |
| 119 | progress | 开始生成正文，进度 50% |
| 120 | content | 第一段内容 |
| 121 | content | 第二段内容 |
| 122 | done | 结果位置 article_001 |

客户端收到并成功应用 120 后断网，此时页面上已经有第一段。

Worker 继续生成第二段并完成任务，121、122 都先写入 Event Store。它能继续运行，依赖任务执行与 SSE 请求生命周期分离；不能仅靠在请求里启动一个异步函数就假定这一点成立。

网络恢复后，客户端携带 120 建立新连接。SSE 接口读取这个任务的后续事件：

```sql
SELECT event_id, type, payload
FROM job_events
WHERE job_id = $1 AND event_id > $2
ORDER BY event_id ASC;
```

其中参数分别是 `job_001` 和 `120`。客户端补上第二段，再处理完成事件并停止订阅。

把整个过程连起来：

```text
创建 Job → Worker 执行
                │
                ▼
        Event Store 保存事件
                │
        按消费位置读取历史与后续事件
                │
                ▼
           SSE Endpoint
                │
                ▼
      Client 更新内容与消费位置
```

这个模型里，**Event Store 保存可恢复的事件事实，SSE 负责传输。** 已提交的事件不会因为一次推送失败就消失。任务能否在 Worker 崩溃后恢复，则属于另一层执行可靠性，需要另行设计。

## 这条主线之外，还有几个实现边界

主线解释了断点续传为什么成立。真正落地时，还需要把几个边界补上，但可以分别研究。

**刷新后，旧内容从哪里恢复？** 如果只保存游标 120，页面内容却清空了，从 121 开始就会缺第一段。可以从头重放保留的历史，也可以先恢复一份“状态 + 对应游标”的快照，再补后续事件。

**历史和实时怎样衔接？** 查完历史再订阅通知，中间可能漏掉刚产生的事件。一种设计是先订阅并保留唤醒标记，始终按游标查询持久日志；通知只负责提醒有新数据，周期性补查覆盖通知丢失。任务内的事件还需要按提交可见顺序推进，避免较小 ID 晚提交而被游标跳过。

**任务完成后怎样结束？** 客户端应在完成事件后停止重连。原生 EventSource 可以调用 `close()`；服务端仅仅结束响应，未必会让它停止重连。[规范对此有明确说明](https://html.spec.whatwg.org/multipage/server-sent-events.html#server-sent-events)。

这些边界不需要混在第一次解释里，但它们决定了一个例子能否变成可靠的实现。

## 回到那个让我卡住的问题

“已经带了事件 ID，为什么还需要去重？”现在可以分两步回答。

正常情况下，客户端确认到 120，服务端只补发 120 之后的事件，这个过程不会重新发送已确认的 120。

但如果处理效果已经生效，而恢复出来的游标还停在 119，服务端就会正确地再次发送 120。这时要保证结果正确，就得处理重复消费，以及状态和游标的一致性。

这次最值得留下来的，是把几个动作分开看：**产生事件、保存事件、发送事件、处理事件、保存消费位置。** 它们之间哪里可能中断，哪里就需要明确恢复规则。沿着这条线再看 SSE，断点续传和幂等就能放回同一个业务过程里理解了。
